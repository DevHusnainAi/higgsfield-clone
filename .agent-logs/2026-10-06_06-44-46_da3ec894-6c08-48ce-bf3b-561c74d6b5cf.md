- **Media type** is decided in this order:
  1. An explicit video word ("video", "clip", "timelapse") or a duration.
  2. An explicit image word ("photo", "illustration").
  3. A camera move, which implies video.
  4. Otherwise, image.
- **Camera moves:** 16 kinds. Each rule needs camera wording, so "frying pan", "tilt-shift" and "the 90s" don't trigger anything.
  - Negation works: "without zooming in" is ignored.
  - If two moves are mentioned, the first one in the prompt wins. When two matches start at the same spot, the longer one wins, so "zoom out" beats "zoom".
- **Aspect ratio:** only colon ratios count, such as "16:9". "2x3 grid" and "2/3 scale" are not read as ratios. Words also work: "tiktok reel" gives 9:16, "anamorphic" gives 21:9, and "square format" gives 1:1.

- **`matched`** records which words in the prompt set each field. Your chips can use it to show what the parser picked up versus what it assumed.

## 1. Real authentication

### Main approach: upgrade the anonymous account, don't switch to a new one
Supabase can turn an anonymous user into a permanent one **while keeping the same user ID**. Every row is keyed by `user_id = auth.uid()`, so history, balance, start frames and rate-limit keys carry over with no data migration and no access-rule changes.

| Method | Call from the anonymous session | Result |
|---|---|---|
| Magic link | `auth.updateUser({ email })` | A confirmation email is sent; clicking it makes the same user permanent |
| GitHub (or Google) | `auth.linkIdentity({ provider: "github" })` | OAuth round-trip, then the same user, now permanent |

The bug to avoid: calling `signInWithOtp` or `signInWithOAuth` while anonymous creates or switches to a **different** user. Their history then disappears behind the access rules, which looks like data loss. Those calls are used only for "sign in on a new device", never for upgrading.

### When the email or GitHub account already belongs to someone
Linking fails with `email_exists` or `identity_already_exists`. The modal then offers "Sign in to your existing account" and brings the anonymous history across:
1. Before redirecting, the browser saves the anonymous access token in `sessionStorage`.
2. After sign-in, it calls `POST /api/account/merge`, sending the old token in the body and the new session as the bearer.
3. The server checks that the old token is valid and anonymous, and that the new user is permanent.
4. A new function, `merge_anonymous_history(from, to)`, callable only by the server, moves the generation rows in one transaction. It runs only once and only from an anonymous source, and then the anonymous user is deleted.
5. **Credits are not transferred.** Otherwise anyone could farm unlimited anonymous 40-credit accounts and merge them into one. Start frames stay behind; they're temporary inputs.
6. If the saved token is more than about an hour old, the merge is refused and the modal says so.
